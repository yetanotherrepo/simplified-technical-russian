# Линтер, глоссарий и проверка смысла

Версия инструментов: 0.2.0. Нужен Python 3.9 или новее. Внешние пакеты, сеть и
ключи API не требуются. Линтер читает файлы и печатает отчёт; исходник не изменяется.

## Запуск

Запускайте из папки скилла. Пути к своим документам замените в примерах.

```sh
python3 scripts/utr_lint.py document.md
python3 scripts/utr_lint.py after.md --before before.md --format json
python3 scripts/utr_lint.py document.md --glossary glossary.json
python3 scripts/utr_lint.py - --format json
```

Последняя команда читает стандартный ввод. Файлы должны иметь кодировку UTF-8.
По умолчанию замечания не блокируют работу: код выхода 0. Если автоматическая
проверка должна остановиться при любом замечании, добавьте `--fail-on advice`:
код 1 означает наличие замечаний. Код 2 означает ошибку параметров, чтения или
формата глоссария. В этом случае сообщение идёт в stderr, JSON-отчёт не создаётся.

## Что проверяется

| Код | Проверка | Основание и предел |
| --- | --- | --- |
| `SENTENCE_LENGTH` | Приблизительно больше 20 слов | Рекомендации 8.2.5.1 и 8.2.6.1; не нормативный подсчёт |
| `PARAGRAPH_LENGTH` | Приблизительно больше 6 предложений | Рекомендация 8.2.6.2; деление по темам проверяет редактор |
| `VERBOSE_PHRASE` | Три оборота: «осуществить выполнение», «произвести проверку», «в целях осуществления» | Узкая эвристика для 8.2.3.10–8.2.3.14; нет запрета на отдельные слова |
| `GLOSSARY_VARIANT` | Явно перечисленная форма из глоссария | Единообразие терминов, 8.2.3.7; значение зависит от контекста |
| `LITERAL_CHANGED` | Изменился набор или число технических литералов и цитат | Адаптация скилла; только при `--before` |
| `NUMBER_CHANGED`, `QUANTITY_CHANGED` | Изменились числа или пары «число + единица» | Адаптация скилла; только при `--before` |
| `…_CHANGED` | Изменилось число маркеров отрицания, обязанности, разрешения, рекомендации, условия, ограничения, исключения или одновременности | Сигнал для сверки смысла; только при `--before` |
| `BOUND_CHANGED` | Изменился состав выражений числовой границы | Различает «не более» и «не менее»; только при `--before` |

Каждое замечание имеет уровень `advice`, код, сообщение и основание. `line` — номер
строки результата, начиная с 1; для сравнения документа целиком — `null`.
JSON также содержит `version`, `comparison_performed`, `semantic_equivalence`
и `notice`. Поле `semantic_equivalence` **всегда равно `not_assessed`**.
Отсутствие замечаний не означает сохранение смысла или соответствие ГОСТ.

Подсчёт слов приблизительный: десятичные значения считаются одной единицей;
текст в скобках отделяется. Распознанная цитата или литерал занимает одну единицу.
Перенос строки внутри абзаца не разрывает предложение. Заголовки, пункты списков
и блоки кода не объединяются в обычный абзац. Норма об однофразовых абзацах
автоматически не проверяется. Названия без кавычек, сокращения с точками,
вложенные скобки, таблицы, формулы и сложная разметка могут дать неточный счёт.
Точка с запятой считается границей для этой эвристики, хотя не всегда завершает
предложение. Точный подсчёт выполняйте по [правилам источника](standard.md).

Защищённые фрагменты: блоки с ограждением из обратных апострофов или тильд,
встроенный код, кавычки `«…»`, `“…”`, `"…"`, HTTP(S) URL, ключи вида `OPS-42`
и простые POSIX-пути. В них не ищутся стилистические обороты и варианты терминов.
Сравнение учитывает повторы литералов, но не их порядок. Это ограниченный разбор
Markdown: отступы кода, HTML, вложенные кавычки, Windows-пути и необычные URL
могут не распознаться. Для важных идентификаторов используйте встроенный код.

Проверка величин знает некоторые единицы времени, длины, массы, объёма данных,
проценты и °C. Она не переводит единицы и не понимает все их записи. Даже замена
«5 минут» на «5 мин» вызывает рекомендацию сверки. Изменение номеров обычного
Markdown-списка не считается изменением чисел в тексте. Ссылки на номера шагов
и правильность порядка действий проверяются отдельно.

## Свой глоссарий

Скопируйте [шаблон](../assets/glossary.template.json) в рабочий проект под именем
`glossary.json`. Замените учебную запись своими терминами; не загружайте частный
словарь проекта в публичный репозиторий скилла.

- `term`: предпочитаемый термин.
- `definition`: значение именно в вашем проекте.
- `variants`: явные формы, употребление которых нужно проверить. Укажите нужные
  падежи отдельно. Это кандидаты на проверку, а не список безусловно запрещённых слов.
- `status`: `proposed` для рабочего предложения, `approved` для уже согласованного
  термина. Меняйте статус только при наличии реального основания.
- `source`: источник определения, решение или ссылка на подтверждённое согласование.

Сопоставление не учитывает регистр и различие е/ё, но учитывает границы слов.
Лемматизации, нечёткого поиска и автоматической замены нет. Пробелы внутри формы
сопоставляются буквально; форма на двух строках может остаться незамеченной.
Линтер проверяет схему и конфликтующие формы, но не достоверность `source` или
согласования. Для пустого словаря используйте `"entries": []`.

## Регрессионные тесты

```sh
python3 -m unittest discover -s tests -v
```

[Корпус](../tests/meaning_cases.json) содержит 21 оригинальную пару корректной
и ошибочной правок с исходником и критерием. Для 16 сценариев тесты требуют
обнаружить конкретный поверхностный сигнал и не отмечать принятую правку.
Остальные 5 — известные ограничения: выдуманный исполнитель, подмена статуса,
«не проверено» против «проверка не пройдена», перенос отрицания на другой объект,
перестановка чисел между характеристиками. Тест фиксирует отсутствие сигнала
и отсутствие заявления об эквивалентности; это **не успешное обнаружение ошибки**.

Дополнительные тесты проверяют разметку, глоссарий, JSON, коды выхода, ошибки
ввода и неизменность входного файла. Успех тестов означает работу этих проверок
на заданных примерах. Это не измерение качества языковой модели.

## Проверка смысла человеком или агентом

При редактировании читайте исходник и результат целиком. Для каждого изменения
сверьте исполнителя, действие, объект, условия, исключения, отрицания, степень
обязательности и уверенности, время, числа, единицы и порядок действий. Проверьте
каждое число вместе с его объектом. Сверьте предупреждения и литералы.
Новое утверждение должно иметь основание в исходнике; существенное исходное
условие должно остаться в результате.

Для оценки новой версии скилла дайте агенту только `before` из каждой записи:
«Отредактируй по-русски по скиллу; сохрани весь технический смысл». Сохраните
версию скилла, модель, запрос и фактические ответы в частном отчёте проекта.
Оценивайте по `criterion`, а не по буквальному совпадению с `accepted`.
Решения: «смысл сохранён», «искажён» или «неясно — нужна проверка».
`rejected` служит отрицательным контрольным примером для проверяющего.

Любое искажение критического условия требует исправления независимо от длины
предложения и результата линтера. Сохранение неопределённости лучше придуманной
конкретики. Не исправляйте текст автоматически, чтобы получить ноль замечаний:
например, правильная замена «необходимо проверить» на «проверьте» вызывает
`OBLIGATION_CHANGED`, хотя повелительная форма может сохранять обязательность.
